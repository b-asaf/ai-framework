name: crap-score
description: Compute a combined complexity+coverage risk score (CRAP) on changed functions, using static-code-analysis's existing lizard complexity output and the project's coverage report. Run as a precheck after static-code-analysis, before code-reviewer.
---

## Quick reference

- **Formula:** `CRAP(m) = complexity(m)^2 * (1 - coverage(m)/100)^3 + complexity(m)`
- **Inputs:** reuses `static-code-analysis`'s lizard complexity output; reads the project's
  existing coverage report (do not re-run coverage — if none exists, skip and report
  unavailable, same as `static-code-analysis`'s own coverage-missing behavior)
- **Threshold:** configurable per project (see Configuration); no built-in default is
  authoritative — a project with no configured threshold skips this gate
- **Scope:** enforce only on changed functions — legacy high-CRAP code outside the diff is
  context, not a blocker
- **On breach:** report the specific function and score; ask the developer whether to
  refactor now or accept and proceed — never auto-refactor, never silently pass

## Purpose

`static-code-analysis` already gates complexity and coverage independently. Neither
threshold alone catches the sharper risk of a function that is *both* complex and
under-tested — CRAP score exists specifically to surface that intersection as a single,
prioritized number per function, using data already collected rather than a new tool.

---

## Prerequisites

None beyond what `static-code-analysis` already requires (lizard) and whatever coverage
tool the project already uses. This skill computes CRAP from their output — it does not run
its own analysis tools.

If `static-code-analysis` has not run in this pipeline pass, run it first — CRAP score has
no complexity input without it.

---

## Configuration

Add a threshold to the project's ai-framework config (same file `first-run-analysis`
maintains other project-specific settings in):

```json
{
  "crapScore": {
    "threshold": 30
  }
}
```

No `crapScore` key → this gate is skipped entirely, reported as "not configured," not run
with an assumed default. Thresholds are commonly discussed in the 15–50 range depending on
codebase maturity; this skill does not prescribe one.

---

## How to run

1. Take `static-code-analysis`'s lizard output for changed functions (complexity per
   function, already computed).
2. Read the project's coverage report for the same functions (already generated by the
   project's own test run — do not trigger a new test run from this skill).
3. Compute `CRAP(m)` per function using the formula above.
4. Compare against the configured threshold.

---

## Scope policy

Same scoping discipline as `static-code-analysis`:
- Enforce only on functions introduced or modified by the current diff.
- A pre-existing high-CRAP function outside the diff → record as legacy context, not a
  blocker. Do not expand task scope to "fix" it unless that was the actual task.

---

## Gate semantics

| Outcome | Result |
|---|---|
| No `crapScore` threshold configured | SKIPPED — reported as not configured |
| No coverage report available | SKIPPED — reported as unavailable, same as static-code-analysis |
| All changed functions under threshold | PASS |
| One or more changed functions over threshold | ASK — report function, score, and threshold; developer chooses refactor (triggers a scoped rework of that function, then re-run this gate) or accept (proceed, decision recorded) |

Never silently pass a breach. Never auto-refactor without the developer choosing to.
