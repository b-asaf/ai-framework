## Quick reference

- **Run:** `hooks/build-verify.sh --lint "<cmd>" --format "<cmd>" --test "<cmd>"` — commands come from `project-overview/sub/stack.md`
- **Pass/fail is the exit code, not your read of the output** — 0 = pass, non-zero = fail. You do not get to decide a failure "doesn't really matter."
- **Retry cap: 3 attempts.** Fix against the failing output each time, not a summary of it.
- **Output is trimmed to ~40 lines by default** on failure — full output is always saved to a log file (path printed alongside the trimmed output), so retries don't re-inject a full noisy dump into your context each time. Use `--full` only for the escalation report on the 3rd failure.
- **On the 3rd consecutive failure of the same stage: stop looping and escalate** — see below. Do not attempt a 4th time.
- **You may not skip a stage because you're confident the code is fine.** If a command is missing from `stack.md`, that's a data gap to flag, not a license to skip.
- **Structural backstop:** `pre-push` runs this again, outside your control, reading `.ai-framework.json` at the repo root — keep that file's commands in sync with what you use here (`first-run-analysis` writes both from the same detection pass).

# Build-verify

## Two layers, not one

There are two separate places this runs, and they exist for different reasons:

1. **Agent-side loop** (this skill, run by `backend`/`frontend`/etc. before declaring done) — fast feedback, catches most failures before you ever see a diff. This is still *instruction-level*: the agent is told to run it and trusted to report the result honestly.
2. **`pre-push` git hook** (`hooks/pre-push`, installed by `python setup.py` via `add_git_template()`, or `git init` to refresh an existing repo) — runs `hooks/build-verify.sh` again, structurally, on the actual `git push`. This is outside any agent's control: it runs whether or not the agent's own loop was honest, skipped, or never triggered. Reads the same lint/format/test commands from `.ai-framework.json` at the project's repo root (generated by `first-run-analysis`, one per repo).

Layer 1 exists so you get fast, cheap feedback without waiting for a push. Layer 2 exists so the gate holds even if layer 1 didn't run correctly — the same "don't trust the builder's self-report" reasoning applied one level further out. If you only want one, layer 2 is the one that actually enforces anything; layer 1 is the one that makes layer 2 rarely trigger.

`.ai-framework.json` is a committed project file containing runnable shell commands, executed automatically on `git push` — same trust tier as `package.json` scripts or a `Makefile`, not a new category of risk, but worth knowing: review changes to it with the same scrutiny you'd give any other file that runs on your machine without a prompt.

## Why this is a separate step, not the builder's own judgment

An agent that just wrote code is the worst-positioned agent to decide whether it's correct — the same reason `code-reviewer` doesn't let the implementing agent review its own PR. Lint/format/test failures aren't judgment calls, though; they're exit codes. There's no reason to route "did the tests pass" through an LLM's opinion when a shell command already gives an unambiguous answer. `build-verify.sh` exists so that signal is deterministic and un-arguable — the builder reacts to it, it doesn't interpret it.

## The loop

1. Read `project-overview/sub/stack.md` for this repo's **Lint command**, **Format command**, **Test command**, **Build command**. If any are still `[XXX]` (unpopulated), stop and trigger `first-run-analysis` rather than guessing a command.
2. Run:
   ```bash
   hooks/build-verify.sh --lint "<lint cmd>" --format "<format cmd>" --test "<test cmd>"
   ```
3. **Exit 0:** proceed to "Before declaring done" in your agent instructions — do not re-run this out of caution, one clean pass is sufficient.
4. **Non-zero exit:** output is trimmed to the last ~40 lines of the failing stage by default — full output is always saved to a log file whose path is printed alongside the trimmed output. For a normal retry, the trimmed tail is enough; fix against it (not a paraphrase of it) and re-run the full command from step 2 — a fix for LINT can reintroduce a FORMAT problem, so always re-run all stages, not just the one that failed. Only read the full log file if the trimmed tail genuinely doesn't contain enough to diagnose the failure — don't cat it by default, that reintroduces the noise the trimming exists to avoid.
5. Count consecutive failures **per stage**. On the 3rd consecutive failure of the same stage, stop — do not attempt a 4th fix.

## Escalation (3rd consecutive failure)

Do not keep retrying. Re-run the failing stage's command with `--full` (or read the log file path already printed) to get the complete output for this one report — this is the one point where the full dump is worth the tokens, since it's a single report to a human, not something re-entering your own context on every retry. Report to the developer:
- Which stage is failing and the exact command
- The full output from all 3 attempts (not summarized — the developer needs to see if the errors are identical, drifting, or oscillating)
- What you changed between each attempt
- Your assessment of whether this looks like a wrong approach (not just a syntax issue) — if so, say so plainly rather than proposing a 4th patch

A 4th silent retry after 3 failures is a sign the approach is wrong, not that the 4th attempt will get lucky. Surfacing this early is cheaper than a developer discovering it later via a failed `/review`.

## Relationship to `code-reviewer` and `static-code-analysis`

`code-reviewer`'s Stage 1 (lint/security scan) still runs at `/review` time — this skill does not replace it, it's a safety net that should now rarely trigger. If build-verify passed honestly, Stage 1 rejecting on the same lint tool would indicate the loop was skipped or gamed, not that the tool disagrees with itself. `static-code-analysis` (lizard/jscpd complexity and duplication) is a separate concern from this skill — build-verify only knows pass/fail from the project's own lint/format/test commands, not complexity thresholds.
